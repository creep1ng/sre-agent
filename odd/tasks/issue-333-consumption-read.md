# Issue #333 — Authoritative Consumption Read

## Objective

Expose an administrator-only API that reads persisted request consumption and returns traceable request, incident, and UTC-month aggregates without treating administrative reads as new consumption.

## Problem and Why

Issue #130 persists consumption evidence per request, but administrators and issue #143 have no bounded, authoritative read projection. Summing browser-visible audit pages can miss records or double-count related events.

## Scope and Constraints

- Reuse persisted #130 consumption evidence and its deny/error/timeout availability semantics.
- Count each effective request once. Keep incident runs distinct and exclude other incidents.
- Define months as half-open UTC calendar ranges; do not accept a local-timezone parameter.
- Report coverage and partial/unknown availability instead of labeling subtotals as complete totals.
- Preserve exact billed USD decimal values and historical pricing context; do not infer missing prices, convert currency, or create billing/enforcement behavior.
- Authorize before returning data or counts. Reject invalid or unbounded filters and surface storage failure as an error.
- Do not load prompts, outputs, provider keys, or unrelated operational records.
- Use real, repeatable API/database evidence. Prefer E2E tests; if isolated tests are necessary, enumerate failure modes before implementation. Never add unit tests after production code.
- Keep technical artifacts in English and avoid invented screenshots or generated captures.

### U333-4 Failure Modes to Cover Before Implementation

- An allowed read returns its normal response only after one committed terminal audit event with the matching status and correlation.
- Authentication failure and authorization denial each produce their governed terminal event before returning 401 or 403; no usage counts leak.
- Covered invalid-selector, overflow, and usage-storage error outcomes remain explicit and are auditable without exposing query data.
- A post-authorization overflow/storage error retains the already-known HMAC-protected principal/resource references and allow decision while recording the terminal validation/audit stage.
- Acceptance assertions verify the exact terminal `reason_code` for each normalized failure outcome and verify pre-authentication events omit identity, resource, and policy decision.
- A post-authorization projection `ValueError`/422 event retains the already-known HMAC-protected principal/resource references and allow decision while recording the validation stage.
- Demo-seed convergence remains idempotent when upgrading from the legacy Alembic revision through the current head, including the additive `usage.read` migration.
- Incident migration downgrade/recovery tests verify the current `head` after upgrading from an older revision; hard-coded pre-follow-up revisions must be updated when the additive migration advances head.
- API readiness must recognize the schema head produced by the additive `usage.read` migration; otherwise `/health/ready` can report PostgreSQL unavailable and prevent the real Compose stack from starting.
- Audit-store failure suppresses an otherwise successful, denied, or normalized-error response and returns safe retryable `503 audit_unavailable`.
- Audit records contain only approved metadata/HMAC projections, never credentials, usage payloads, prompts, or provider data.
- Usage reads use the dedicated `usage.read` operation so they cannot enter the `responses.create` evidence query.
- The audit write uses a short transaction and does not hold the usage read transaction open through response release.

## Acceptance Criteria

- CA1: Repeated reads and related events never double-count a known effective request.
- CA2: An incident includes its distinct runs, excludes other incidents, and UTC-month boundaries are exact. Each effective request is attributed only to the UTC month of its earliest persisted `responses.create` event; related rows from later months are included in that canonical month for deduplication and coverage.
- CA3: Missing tokens or prices retain partial/unknown coverage; subtotals are not presented as complete totals.
- CA4: Cost retains currency, billed nature, decimal precision, and historical price version; incompatible values are not combined.
- CA5: Deny, error, and timeout follow #130 uncertainty semantics.
- CA6: Non-admin access reveals no data/counts; invalid or unbounded filters fail; storage outage is not an empty result.
- CA7: Reads require only persisted evidence, not prompts/outputs/keys, and month tests use controlled instants.
- CA8: The governed usage read commits one metadata-only terminal audit event for each covered outcome before returning it; if that commit fails, the route suppresses the intended response and returns `audit_unavailable`.
